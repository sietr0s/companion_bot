# Architectural Audit: Modular Monolith

Систематическая методология аудита архитектуры Modular Monolith на Python/FastAPI/SQLAlchemy. Выявляет расхождения между заявленным архитектурным стилем и реальной кодовой базой.

## Этапы аудита

### 1. Загрузка заявленной архитектуры

Прочитать документы, описывающие целевой стиль:
- `GIGACODE.md` / `README.md` — общие принципы, структура, правила
- `STYLEGUIDE.md` — паттерны, соглашения, антипаттерны
- `docs/architecture.md` — если есть

Зафиксировать ключевые правила, которые будем проверять:
- Изоляция модулей (нет прямых импортов)
- DI-зависимости в модулях, не в ядре
- Сервисы → репозиторий (нет `session.add/commit/execute` в сервисах)
- Исключения вместо `None`
- Межмодульное взаимодействие через шину/клиенты
- Доменные модели отделены от DTO/схем

### 3. Проверка по измерениям

#### Изоляция модулей
- Искать `from src.modules.<X>` внутри `src/modules/<Y>` где X ≠ Y
- Искать `from src.modules.` внутри `src/core/`
- `main.py` — composition root, импорты из модулей допустимы
- `core/clients/` — импорты из модулей допустимы (паттерн Clients)

#### DI-зависимости
- Каждый модуль должен иметь `dependencies.py`
- `core/dependencies.py` — только общие зависимости (сессия, JWT, клиенты)
- Нет импортов модульных сервисов в `core/dependencies.py`

#### БД-паттерн (Сервис → Репозиторий)
- Искать `session.add(`, `session.commit(`, `session.execute(` в `service.py`, `handlers.py`
- Допустимо только в `repository.py`
- Проверить, что `repository.delete/update` получают ORM-объект, а не ID

#### Обработка ошибок
- Сервисы выбрасывают `AppException` (NotFoundError, ConflictError, UnauthorizedError)
- Нет `return None` в сервисах при ошибке
- Нет `try/except` в роутерах (глобальный handler)
- `try/except` допустим на границах (внешние API, клиенты)

#### Межмодульное взаимодействие
- Проверить использование шины: публикация через `message_bus.publish(BusTopics.X)`
- Проверить использование клиентов: `src/core/clients/`
- У всех клиентов единый паттерн создания (DI vs ручное инстанцирование)
- Клиенты используют общую шину, а не изолированный `InMemoryProducer`

#### Доменные модели
- Проверить наличие `domain/` в модулях
- Сервисы возвращают доменные модели, не DTO/схемы
- Маппинг домен → DTO на уровне роутов/мапперов

#### Структурная согласованность
- Все модули имеют единый набор файлов: `models.py`, `repository.py`, `service.py`, `handlers.py`, `dependencies.py`, `schemas/`, `routers/`
- Все модули документированы в GIGACODE.md/README.md
- Обработчики в `handlers.py` содержат бизнес-логику, а не только логирование

### 5. Итоговый отчёт

Формат выдачи:
1. **Критические проблемы** — bugs, которые надо чинить немедленно
2. **Нарушения изоляции** — прямые импорты между модулями/из ядра
3. **Нарушения паттернов** — БД, ошибки, клиенты
4. **Структурные несоответствия** — missing files, undocumented modules
5. **Сводная таблица** — все находки с файлами и серьёзностью
6. **Приоритетные действия** — что чинить в первую очередь

## Типовые нарушения и как их фиксить

### 🔴 Передача ID вместо ORM-объекта в repository

**Симптом:** `repository.delete(session, account.id)` / `repository.update(session, account.id, data)`

**Почему падает:** `BaseRepository.delete/update` делают `session.delete(obj)` / `setattr(obj, field, value)` — ожидают ORM-объект, получают UUID/int → `AttributeError` в рантайме.

**Как искать:** `grep -rn "repository\.\(update\|delete\)(session, \w+\.id" src/modules/`

**Исправление:** передавать ORM-объект: `repository.delete(session, account)`

### 🟠 Прямой импорт между модулями

**Симптом:** `from src.modules.job_matcher.repository import ...` внутри `src/modules/job_bot/dependencies.py`

**Почему плохо:** при выносе модуля в микросервис ломается импорт. Модуль-транспорт (job_bot) знает о бизнес-логике (job_matcher).

**Исправление:** фабрика сервиса должна быть в самом модуле (`job_matcher/dependencies.py`), а внешний код получает её через partial/DI.

### 🟠 Ядро импортирует модули

**Симптом:** `from src.modules.auth.service import AuthService` внутри `src/core/seed.py`

**Почему плохо:** `core/` — инфраструктурный слой, не должен знать о бизнес-модулях.

**Исправление:** перенести seed-логику в модуль (`auth/seed.py`) или в `main.py` (composition root).

### 🟡 `session.execute()` в сервисе в обход репозитория

**Симптом:** сервис вручную строит `select(Model).options(selectinload(...))` и вызывает `session.execute()`

**Почему плохо:** смешивает бизнес-логику с персистентностью, нельзя замокать репозиторий в тестах.

**Исправление:** добавить метод в репозиторий (например, `get_by_auth_id_with_telegram`) и вызывать его из сервиса.

### 🟡 `session.commit()` в обработчиках шины

**Симптом:** `handlers.py` вызывает `await session.commit()` после вызова сервиса

**Почему плохо:** управление транзакциями — ответственность репозитория/сервиса, не обработчиков.

**Исправление:** `BaseRepository.create/update/delete` уже делают `commit()` внутри — вызов в handlers избыточен. Убрать.

### 🟠 Изолированный InMemoryProducer в клиентах

**Симптом:** `UsersClient.__init__` создаёт `InMemoryProducer()` по умолчанию, если `message_bus` не передан

**Почему плохо:** события, публикуемые через такого клиента, не доходят до подписчиков на общей шине.

**Исправление:** клиент должен получать сервис через DI-фабрику (как `MediaClient`), которая внедряет общую шину через `get_message_bus`.

### 🟡 Мёртвый `dependencies.py` с кросс-модульными импортами

**Симптом:** `job_bot/dependencies.py` импортирует из `job_matcher`, но сам файл никем не импортируется

**Исправление:** удалить кросс-модульные импорты, оставить заглушку для будущих зависимостей модуля.

### 🟡 Отсутствие `handlers.py` в модуле-издателе

**Симптом:** модуль `auth` публикует события, но не имеет `handlers.py`

**Исправление:** создать `handlers.py` с заглушкой `register_handlers()` (как в `media/handlers.py`) — для структурной согласованности.

### 🟡 Модуль не документирован

**Симптом:** `classifier` отсутствует в GIGACODE.md и README.md

**Исправление:** добавить модуль в структуру проекта и таблицу модулей.

## Примечания

- `main.py` — composition root, прямые импорты из модулей здесь допустимы
- `core/clients/` — импорты из модулей допустимы (это паттерн Clients)
- `core/` не должен импортировать модули (кроме `clients/`)
- Репозитории — единственное место для `session.add/commit/execute`
- Обработчики шины не управляют транзакциями (нет `session.commit`)
- `core/telegram_manager.py` — осознанный workaround для циклической зависимости, не нарушение
